# Phase 6 plan: finishing the master prompt's delivery plan

*Agreed 2026-11-03: the user chose this phase ("finish the master prompt's delivery plan") and made the two decisions below.*

Phases 1–5 built every module, the predictive core, the industry views and a real backend. What the master prompt asked for and never got is mostly **around** the app rather than in it: its delivery plan's last step ("testing & quality, documentation and a demo walkthrough script for stakeholders", §11, step 10 of the [architecture's delivery plan](01-architecture/README.md)), the quality expectations of §10 (a CI pipeline, a component catalogue with every state, a contribution guide), and three items every review since Phase 1 has carried forward: Storybook, virtualised tables and the synchronised event-timeline canvas. The repository is now public on GitHub, so this is also what visitors will meet first.

**What chunk 1 added:** [ADR-0018](adr/0018-ci-on-github-actions.md): `.github/workflows/ci.yml` (every push and pull request: `npm run check` and `npm run e2e:server` on two machines side by side) and `e2e-demo.yml` (the demo-mode suite every Monday and on demand), on `ubuntu-24.04` (which has Chrome and Node 24), read-only permissions, actions pinned to exact commits, time limits, failure evidence kept 14 days; a CI badge in the README. See [learning note 45](learning/45-continuous-integration.md).

**What chunk 2 added:** measured first: of the four lists, only the **alarm list** draws everything at once (up to 500 rows; the registry, tag browser and audit log are already paged by 50), and as every row shows "raised … ago", all of it redraws every second: with 266 alarms the page froze for 52–106 ms each second, and a checkbox took 100 ms. Above 60 rows, `AlarmTable` now draws only the rows in view and 8 either side (TanStack Virtual 3.14.21, pinned), measuring each row as it's drawn; group headings flow with the rows; `aria-rowcount` and `aria-rowindex` tell screen readers the whole list's size and each row's place; ↑/↓ scroll a row into view before focusing it, and quick presses count from the row on its way. Re-measured: 16 rows drawn instead of 266, no long tasks idle or while scrolling, axe clean in light and dark, no overflow at phone width. Where a page can't be measured (the unit tests' jsdom) the whole list is drawn, as before. A demo-mode browser test checks it, and fails with virtualisation off. See [learning note 46](learning/46-drawing-only-what-shows.md).

**What chunk 3 added:** a new `EventLanesChart` in `@pdm/charts` draws events as marks in five lanes (alarms, operator actions, maintenance, process, predictions), coloured by severity, with a slider to zoom. On Asset 360's **Telemetry** tab it sits under the sensor charts; all of them share one time axis: the same range, the same left margin (so the axes line up to the pixel) and one `echarts.connect` group, so zooming or panning any chart moves the rest, and the heading says which window they all show. Each chart remembers its zoom when it redraws with new data, and a sensor ticked while zoomed joins at the group's zoom (both used to reset). On the alarms page's **Timeline** view the lanes sit above the list, and the list keeps to the part in view. Click an event, or use ← → with the lanes focused, and it's described below with a link to its alarm, work order or prediction; + − zoom, Shift+← → pan, 0 shows everything. Without canvas the lanes aren't drawn and the list carries everything, as before. Two demo-mode browser tests check it (the sync test fails if the charts aren't connected), and axe passes on both pages. See [learning note 47](learning/47-one-time-axis.md).

**What chunk 4 added:** a new workspace, `apps/catalogue`, holds Storybook 10.6.5 (pinned) and 43 stories of every shared component in `packages/ui` and `packages/charts`: buttons, form fields, health and priority badges, KPI cards, dialogs, side sheets and popovers, and the time-series and event-lane charts. The states: loading, empty, failed (a crash caught by the error boundary), stale data (gaps in readings, doubtful-quality readings), extreme values (huge and negative numbers, long labels, a spike, an alarm flood of 300 events). `npm run storybook` opens it; a toolbar switches between the three themes. `npm run test:stories` opens every story in every theme in Chrome: axe must find nothing (it doesn't), and on this laptop each must match its saved screenshot (129). GitHub runs the accessibility half as a third CI job. The screenshots found a bug in the first setup: charts drew in the previous theme's colours, because the theme was set after they'd drawn. The packages themselves didn't change. See [ADR-0019](adr/0019-component-catalogue.md) and [learning note 48](learning/48-a-catalogue-of-parts.md).

**What chunk 5 added:** the **waterfall** and the **orbit** on Asset 360's Vibration tab, the last charts without one, now have a cursor for the keyboard and the mouse, like the spectrum's: on the waterfall ← → move along the frequencies (Shift for ten lines, Home/End for the ends) and ↑ ↓ between weeks; on the orbit ← → move along the shaft's path, Page Up/Down a whole turn. Each says where it is in words under the chart ("14 Oct: 150 Hz, 0.917 mm/s"; "Turn 2 of 4, 15° after the once-per-turn mark: X −0.8 µm, Y 3.0 µm"), which screen readers announce; the keys are described to them too. A unit test drives both from the keyboard; axe and the phone-width check still pass on both vibration pages. A **[screen-reader test script](testing/nvda-script.md)** walks through eight journeys with NVDA in about 45 minutes, saying what you should hear at each step, for you to run; what it finds gets fixed. See [learning note 49](learning/49-listening-to-the-app.md).

## Not in Phase 6

From the prompt, still open after this phase, for a later choice: turnarounds and critical-path shutdown planning; feature flags (there's no rollout audience yet); scheduled and emailed reports; the deployment items listed in the [Phase 5 review](phase-5-review.md); a real AI model; real OEE.

## Things to keep in mind

- **Nothing in the app changes behaviour** except the timeline (new) and the waterfall and orbit (keyboard cursors). Virtualised tables must look and behave the same.
- The budgets still hold, `npm run check` before every commit, and **every commit is pushed** to the public repository: no secrets, nothing personal.
